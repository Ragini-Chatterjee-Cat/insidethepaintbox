What happens when a visitor sends a message
1
Chat widget sends the message + thread_id to Railway via POST /chat/v2.
2
FastAPI calls chat_with_memory() → the compiled LangGraph graph is invoked.
3
Graph runs: loads preferences → classifies intent → routes to artwork / general / commission handler → extracts & saves preferences.
4
Artwork questions trigger the ReAct loop with ChromaDB lookups via Groq. Commission questions start a multi-turn intake conversation.
5
Final AI response is returned to the chat widget. The full trace appears in LangSmith.

RAG Pipeline — inside react_node

1
Embed
The query is converted into a 384-dimensional vector using SentenceTransformer all-MiniLM-L6-v2. Runs locally on Railway — no API call, no cost.
→
2
Retrieve
Vector is queried against ChromaDB (local, persistent). Returns top 5 most semantically similar artwork documents. Results with distance above 1.5 are filtered out as low-confidence.
→
3
Generate
Groq (Llama 3.3 70B) receives retrieved context + conversation history. Returns a warm, gallery-guide-style answer with correct artwork URLs.
What gets indexed into ChromaDB
On startup, document_loader.py scrapes every artwork page (artworks/*.html), every series page (pages/series/*.html), and the About page using BeautifulSoup. Each page becomes one document stored with title, series name, and URL as metadata.

URL fix: both html_path and website_path are resolved to absolute paths before .relative_to() — preventing the old fallback that generated bare filenames like /Voices.html.
Series URL map (hardcoded in tools.py)
filter_by_series always returns the correct series page URL from a static SERIES_URLS dict — the LLM never guesses a URL. Covers all 8 series: Portraits, Animal Portraits, Mythical, Thoughts, Camera Series, Diary Entries, Fanart, Cards.

5 LangChain tools — available to the ReAct loop

search_artworks(query)
Semantic similarity search across the full ChromaDB collection. Embeds the query and returns up to 5 artworks with titles, series, descriptions, and URLs. Filters results above distance 1.5.
NOT used for specific titles or series names.
"Show me something dark and emotional" "Do you have anything about mythology?"
filter_by_series(series)
Lists all artworks in a specific series. Always returns the correct series page URL from the hardcoded SERIES_URLS map. Falls back to SERIES_ARTWORK_MAP if ChromaDB returns nothing.
Explicit docstring: do NOT call for individual artwork names.
"Show me all the Mythical artworks" "What's in the Diary Entries series?"
get_artwork_details(artwork_name)
Looks up a specific artwork by title. Semantic search + exact title match preference.
Explicit docstring: do NOT use for series names — use filter_by_series instead.
"Tell me about Voices" "What is Icarus about?"
get_commission_info()
Returns static commission info — no arguments, no DB call. Includes contact links, commission types, and response time. Hardcoded in tools.py.
Note: the new commission_intake node handles interactive commission requests.
"How do I commission a piece?"
recommend_similar(artwork_name)
Two-step search: finds the source artwork's full document, embeds the entire content, then queries ChromaDB for thematically similar pieces. Returns up to 4 results excluding the source.
"I liked Icarus, show me more like it" "Recommend something like Trapped"
How the ReAct loop uses these tools
The LLM sees all 5 tool definitions in its context. Each iteration it outputs either a tool call (JSON with name + arguments) or a plain text response (the final answer). Tool calls are executed by LangGraph's built-in ToolNode, the result is appended as a ToolMessage, and the loop continues for up to 5 iterations. A complex question like "Tell me about Icarus and recommend something similar" triggers two tool calls in sequence.

Two-layer memory system

Layer 1 — SQLite
Managed automatically by LangGraph's SqliteSaver checkpointer
Stores the full message history — every HumanMessage and AIMessage per thread
Keyed by thread_id — a UUID generated in the browser, stored in localStorage
Persists across sessions — revisiting the site resumes the exact conversation
Cleared on "new conversation" via DELETE /chat/history/{thread_id}
Layer 2 — JSON files (user_prefs/)
One file per visitor: user_prefs/{thread_id}.json
Stores extracted interests — not raw messages
Updated after every exchange by extract_preferences
Loaded at session start by load_preferences, injected as system context
Commission requests stored as {thread_id}_commission.json
Ragini's replies stored as {thread_id}_reply.json
{
  "liked_series": ["Mythical", "Portraits"],
  "mentioned_artworks": ["Icarus", "Voices"],
  "tone": "curious"
}
Why two layers?
SQLite holds the raw message log so the LLM can resolve follow-up references ("tell me more about it"). The JSON preference file holds a distilled, high-level summary injected as system context — so even the very first message of a new session feels personalised. Clearing a conversation deletes both the SQLite checkpoint rows and the JSON file.

Human-in-the-loop commission flow

💬
Visitor expresses interest
The visitor types something like "I'd like to commission a portrait". The classify node detects intent = commission and routes to commission_intake.

"Hi! I'd love to commission a pet portrait."
✏️
Bot collects details, one question at a time
The intake node gathers all required info across multiple turns:
  • Type of piece — portrait, pet portrait, illustration, or card
  • Subject — who or what the piece is of
  • Occasion or purpose — gift, keepsake, event
  • Style preferences — or browse existing series for reference
  • Timeline — any deadline or flexible?
  • Contact details — email or Instagram handle (required before filing)
📁
Request filed + visitor confirmed
Once contact details are collected, the node writes user_prefs/{thread_id}_commission.json with the full summary and timestamp. The visitor receives a warm confirmation:

"Thank you so much! I've passed everything on to Ragini — she'll be in touch via Instagram or email within a few days."
The chat widget begins polling GET /chat/updates/{thread_id} every 30 seconds for up to 30 minutes, waiting for Ragini's reply.
🗂️
Ragini checks her admin inbox
Ragini visits insidethepaintbox.netlify.app/admin.html, enters her ADMIN_TOKEN password, and sees all pending commissions with summaries, timestamps, and contact details. The page auto-refreshes every 30 seconds.

Endpoint: GET /admin/pending (Bearer token auth via Railway env var)
✍️
Ragini writes a personal reply
In the admin inbox, Ragini types a personal note and clicks Send Reply. This calls POST /admin/respond/{thread_id} and saves the reply to user_prefs/{thread_id}_reply.json.
💌
Reply appears in the visitor's chat
The next poll picks up the reply from /chat/updates/{thread_id} and it appears in the chat widget as a new message — no page refresh needed. If the visitor has already closed the tab, Ragini uses their contact details (email or Instagram) to follow up directly.

"💌 A personal note from Ragini: Hi! I'd love to paint your pup — let's chat about references and style. I'll DM you on Instagram!"
