⬡ Phase 1 · Startup · Runs once when FastAPI boots
load_all_artworks()
Scans /artworks/ and /pages/artworks/ for HTML files. For each, calls load_artwork_from_html(). Also loads /pages/series/ HTML pages for extra context.
INwebsite root path
OUTList[Dict] — all artwork docs
What it extracts per HTML page
• h1 → artwork title
• h6 → subtitle / dimensions
• p tags → description
• h2 → section headers (e.g. INSPIRATION)
• Series membership via SERIES_ARTWORK_MAP
• Live Netlify URL (so chatbot can share links)
Why scrape your own HTML?
Your artwork descriptions are in HTML, not a spreadsheet. Scraping them at startup keeps the chatbot in sync with your website automatically — update an artwork page, call /reindex, done.
load_about_page()
Separately loads pages/about.html and renames its title to "About the Artist". Ensures the chatbot can answer questions about you, not just your art.
INwebsite root path
OUTSingle about-page Dict
Separation of concerns
About page lives in /pages/, not /artworks/, so the glob pattern in load_all_artworks() misses it. Explicit handling ensures it's always indexed alongside the artworks.
index_documents()
Clears the ChromaDB collection, re-embeds every document with all-MiniLM-L6-v2, and stores embeddings + metadata (title, series, URL, source path). Fresh index on every restart.
INList[Dict] artwork docs
OUTChromaDB collection (persisted)
✓ ChromaDB chosen because
Zero-config, embedded in the Python process, stores to disk automatically. Supports metadata filtering natively. Ideal for a small corpus (<100 artworks) on Railway where you want no external services.
✗ Rejected
FAISS
Pinecone
FAISS doesn't natively store metadata; needs manual management. Pinecone is a paid service. ChromaDB handles both with one call.
⬡ Phase 2 · RAG Pipeline · Runs on every user message
build_search_query()
Enriches the user's query by appending the last 2 user turns from conversation history. Turns "what colors does it use?" into a meaningful embedding query by adding prior context about what "it" refers to.
INquestion + history[-4]
OUTenhanced query string
The pronoun problem
Short follow-ups like "tell me more" or "what inspired it?" embed poorly — they have no semantic content without context. Prepending prior user messages gives the embedding model enough signal to find the right artwork.
✗ Rejected
raw question only
Would retrieve wrong/generic results for any follow-up question. The 2-step CoT reasoning still resolves this later, but better retrieval upstream means better answers.
search_similar()
Embeds the enhanced query with all-MiniLM-L6-v2, queries ChromaDB for top k=3 nearest documents. Returns content, metadata (title/series/URL), and L2 distance score.
INenhanced query, k=3
OUTList[{content, metadata, distance}]
Small corpus, high precision
With ~50 artworks, k=3 retrieves exactly the relevant pieces without injecting noise. Each artwork document is richly described, so 3 is sufficient. Compare with ESRS (k=15, 1000+ regulatory paragraphs).
generate_response() 2-step CoT
Two sequential Groq API calls. Step 1: reasoning prompt — resolves intent, pronouns, and relevant context. Step 2: response prompt — uses Step 1's analysis to write a warm, gallery-guide answer.
INquestion + docs + history
OUTFinal answer string
Step 1 — Reasoning (temp=0)
Asks: "What does the user want? What's 'it'? What's relevant in the context?" Also has access to the full SERIES_ARTWORK_MAP so it knows which artworks exist. Prints to server log for debugging.
Step 2 — Response (temp=0)
Uses Step 1's analysis as its "thinking" input. Only writes the final visitor-facing message. Keeps it concise (1–3 sentences). Shares artwork URLs only when asked.
Confidence threshold
Docs with distance > 1.5 are flagged as low-confidence and handled separately. Prevents the LLM from hallucinating based on vaguely relevant context.
✗ Rejected
single LLM call
A single prompt struggles with pronoun resolution and intent disambiguation simultaneously. Separating reasoning from response improves coherence significantly.
⬡ Phase 3 · Memory Layer · Persistent across sessions
chat_with_memory()
Entry point for /chat/v2. Accepts a thread_id (stored in browser's localStorage). Invokes the LangGraph graph with the user's message; the graph checkpointer auto-loads prior state from SQLite.
INmessage + thread_id
OUTassistant response string
✓ LangGraph chosen because
Provides a proper stateful graph abstraction with a built-in checkpointing API. The SqliteSaver persists conversation state to a local file — no external database needed. Messages are auto-accumulated via the add_messages annotation.
✗ Rejected
client-side history (legacy /chat)
The old /chat endpoint requires the frontend to send the full history on every request. Loses history on page refresh. Breaks if the user opens a second tab.
process_message() (LangGraph node)
The single node in the conversation graph. Converts LangGraph message objects into the history dict format expected by the RAG pipeline, calls query_rag(), and returns the response to be checkpointed.
INConversationState (accumulated msgs)
OUTUpdated state + current_response
Graph: START → process → END
Intentionally simple — a single node. LangGraph's value here isn't the graph complexity but the checkpointer: every graph invocation is automatically saved to SQLite keyed by thread_id. No custom storage code needed.
ConversationState schema
messages: Annotated[list, add_messages] — the add_messages annotation means messages are appended, never overwritten. current_response: str — extracted after invocation to return to the API caller.
get / clear conversation_history()
History retrieval reads the LangGraph checkpoint state for a given thread_id. Clearing directly deletes rows from the SQLite checkpoints table by thread_id.
INthread_id
OUTList[{role, content}] or success bool
Browser side
On first visit, chat.js generates a UUID and stores it in localStorage. Every subsequent request sends the same thread_id, so the server always loads the right conversation from SQLite.
Multi-session persistence
Close the tab, reopen tomorrow — same thread_id in localStorage, same conversation history from SQLite. Completely invisible to the user but creates a continuous conversational experience.
⬡ Phase 4 · Frontend · Static HTML/JS (Netlify)
chat.js
Manages the chat widget. Generates or retrieves thread_id from localStorage, sends messages to /chat/v2, renders responses. Handles the UI state (typing indicator, scroll, message bubbles).
INUser input + localStorage thread_id
OUTPOST to /chat/v2 + rendered message
Static HTML, not a framework
No React, no build step. The site is a pure HTML/CSS/JS portfolio — fast to load, easy to maintain, deploy instantly to Netlify as static files. The chat widget is the only dynamic piece, isolated in chat.js.
carousel.js + tilted-card.js
Visual flourishes for the portfolio. carousel.js handles the series image carousels on artwork pages. tilted-card.js adds 3D perspective tilt on hover to artwork cards on the homepage and series pages.
INDOM elements + mouse events
OUTCSS transforms / transitions
decision-tree-game.js + hyperplane-game.js
Interactive ML-concept games embedded in the portfolio. The hyperplane game visualises an SVM decision boundary; the decision tree game lets visitors split data. A creative intersection of your art and data science interests — makes the portfolio memorable.
8 Series + Artwork Pages
Portraits · Animal Portraits · Mythical · Thoughts · Camera Series · Diary Entries · Fanart · Cards. Each series has a page; each artwork has its own HTML with title, description, inspiration, and image.
INStatic HTML files
OUTParsed by document_loader.py at startup
The website IS the data source
There's no separate data file or spreadsheet. document_loader.py reads the same HTML files your visitors see. Adding a new artwork page automatically adds it to the chatbot's knowledge — just call /reindex.

Design Choices · Head-to-Head
LLM Provider
USED
Groq API — LLaMA-3.3-70b
Extremely fast inference (tokens/s). Free tier available. 70b model quality for nuanced art descriptions. No local GPU needed.
ALT
OpenAI GPT-4
Higher cost per call. Slower on Railway's free tier. Groq gives comparable quality at much higher speed for a conversational art guide.
Conversation Memory
USED
LangGraph + SQLite (thread_id)
Server-side persistent state. Works across tabs and page refreshes. Zero frontend complexity — just store a UUID in localStorage.
ALT
Client-side history array (/chat)
Frontend must track and send full history every time. Lost on refresh. Breaks on mobile where tabs are killed. Still available as legacy endpoint.
Response Generation
USED
Two-step Chain-of-Thought
Step 1 resolves intent and pronouns. Step 2 writes the response. Handles ambiguous follow-ups without hallucinating.
ALT
Single prompt RAG
Works for direct questions but fails on "tell me more about it" type follow-ups — the model guesses what "it" means and often gets it wrong.
Document Source
USED
Live HTML scraping at startup
Website IS the knowledge base. Update artwork HTML → call /reindex → chatbot knows immediately. No separate data maintenance.
ALT
Separate CSV / JSON data file
Would require maintaining two sources of truth — the HTML page and the data file. Drift is inevitable.
Frontend Framework
USED
Vanilla HTML/CSS/JS
Zero build toolchain. Netlify deploys in seconds. Fast load time. Full visual control for an art portfolio — no framework constraints.
ALT
React / Next.js
Overkill for a portfolio of static pages. Adds build steps, bundle size, and complexity with no benefit for this use case.
Retrieval Confidence
USED
Distance threshold (> 1.5 = low)
Low-confidence docs are flagged so the LLM knows context may not be relevant. Prevents confident-sounding wrong answers.
ALT
Always inject top-k regardless
Works when the corpus fully covers the question space. For an art site, users might ask off-topic questions — threshold gives an honest "I don't know".
