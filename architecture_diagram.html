What happens when a visitor sends a message
1
Chat widget sends the message + a thread_id to Railway via POST /chat/v2.
2
FastAPI calls chat_with_memory() which invokes the compiled LangGraph graph.
3
LangGraph runs 6 nodes — loads preferences, classifies intent, routes to the right handler, extracts new preferences, and saves them.
4
If the message is art-related, the ReAct loop calls tools against ChromaDB and generates a response via Groq.
5
The response is returned to the chat widget. The full trace appears in LangSmith.

classify
Intent router
A tiny, fast LLM call (max_tokens=5) that asks Groq one question: is this message about artwork or general chat? Returns a single word. This gates the expensive ReAct loop so small talk never triggers a full RAG search.

artwork — series, specific pieces, commissions, recommendations
general — greetings, small talk, off-topic questions
conditional edge
3a
react_node
if intent = "artwork"
The ReAct loop. The LLM is bound with all 5 artwork tools and iterates up to 5 times. Each iteration: the LLM decides whether to call a tool or return the final answer. If a tool is called, the result is appended as a ToolMessage and the loop continues.

User preferences are injected as a SystemMessage so responses feel personalised.

Error handling: The entire loop is wrapped in a try/except. If Groq returns a 400 (malformed tool call), the node catches it and returns a friendly fallback message instead of crashing the request with a 500.
3b
general_chat
if intent = "general"
No tools. A single LLM call (max_tokens=200) with a friendly system prompt. Responds warmly and tries to gently steer the conversation toward the art collection. Keeps replies to 1-3 sentences.
both paths merge here
4
extract_preferences
Learning
After every response, an LLM call analyses the last 2 exchanges and extracts which series the visitor engaged with, which artwork titles were mentioned, and their tone. Merges with existing preferences (capped at 10 series, 20 artworks). This is how the agent learns about the visitor without asking them directly.
always
5

Disk write
Writes updated preferences back to user_prefs/{thread_id}.json. This is the cross-session memory layer — separate from the SQLite message history. Next time the same visitor opens the chat, load_preferences reads this file and the agent already knows their interests.

RAG Pipeline — inside react_node

1
Embed
The query is converted into a 384-dimension vector using SentenceTransformer all-MiniLM-L6-v2. Runs locally on Railway — no API call, no cost.
→
2
Retrieve
The vector is queried against ChromaDB (local, persistent). Returns the top 5 most semantically similar artwork documents. Results with distance above 1.5 are filtered out as low-confidence.
→
3
Generate
Groq (Llama 3.3 70B) receives the retrieved context + conversation history. Uses two-step Chain-of-Thought. Returns a warm, gallery-guide-style answer.
Two-Step Chain-of-Thought in generate_response()
A
Reasoning pass — LLM is given the question, conversation history, and retrieved docs. Asked to identify what the user actually wants (resolves pronouns like "it", "that"), which parts of context are relevant, and what 1-2 key points to include. max_tokens=300, temperature=0
B
Response pass — A second LLM call receives the reasoning as context and writes the final visitor-facing response. Warm, concise (2-4 sentences), never fabricates. max_tokens=250, temperature=0
What gets indexed into ChromaDB
On startup, document_loader.py scrapes the website's HTML using BeautifulSoup — every individual artwork page (artworks/*.html), every series page (pages/series/*.html), and the About page. Extracts titles, subtitles, paragraph descriptions, and section headers. Each page becomes one document stored with title, series name, and URL as metadata.

URL fix: Both html_path and website_path are resolved to absolute paths before calling .relative_to(). Previously the mix of relative and absolute paths always hit the ValueError fallback, generating bare filenames like /Voices.html instead of the correct /artworks/Voices.html.

5 LangChain Tools — available to the ReAct loop

search_artworks(query)
Semantic similarity search across the full ChromaDB collection. Embeds the query and returns the top 5 artworks with titles, series, descriptions, and URLs. Filters results above the confidence threshold of 1.5.
Triggered by descriptions, themes, moods
"Show me something dark and emotional"

"Do you have anything about mythology?"
filter_by_series(series)
Lists all artworks in a specific series. Always returns the correct series page URL from a hardcoded SERIES_URLS map — the LLM never guesses the URL. Falls back to SERIES_ARTWORK_MAP if the ChromaDB query returns nothing.
Triggered when a series name is mentioned directly. The tool description explicitly tells the LLM NOT to use get_artwork_details for series names.
"Show me all the Mythical artworks"

"What's in the Diary Entries series?"
get_artwork_details(artwork_name)
Looks up a specific individual artwork by title. Does a semantic search then checks for an exact title match to prefer precise hits. The description explicitly says: do NOT use this for series names — use filter_by_series instead.
Triggered ONLY when a specific artwork title is named, not a series
"Tell me about Voices"

"What is Icarus about?"
get_commission_info()
Returns static commission information — no arguments, no DB call. Includes contact links, commission types (portraits, illustrations, cards), and response time. Hardcoded in tools.py.
Triggered by commission / ordering questions
"How do I commission a piece?"

"Can I order a custom portrait?"
recommend_similar(artwork_name)
Two-step search: finds the source artwork's full document, then embeds that entire document to find thematically similar pieces. Returns up to 4 recommendations, excluding the source itself.
Triggered by "more like this" requests
"I liked Icarus, show me more like it"

"Recommend something like Trapped"
How the ReAct loop uses these tools
The LLM sees all 5 tool definitions as part of its context. Each iteration it outputs either a tool call (JSON with tool name + arguments) or a plain text response (the final answer). Tool calls are executed by LangGraph's built-in ToolNode, the result is appended as a ToolMessage, and the loop continues for up to 5 iterations. A complex question like "Tell me about Icarus and recommend something similar" will trigger two separate tool calls in sequence.

Two-Layer Memory System

Layer 1 — SQLite (conversation_memory.db)
Managed by LangGraph's SqliteSaver checkpointer automatically
Stores the full message history — every HumanMessage and AIMessage per thread
Keyed by thread_id — a UUID generated in the browser and stored in localStorage
Persists across sessions — revisiting the site resumes the exact conversation
The full LangGraph state is checkpointed here after every node completes
Layer 2 — JSON files (user_prefs/)
One file per visitor: user_prefs/{thread_id}.json
Stores learned preferences — not raw messages, but extracted interests
Updated after every exchange by extract_preferences
Loaded at the start of every session by load_preferences
Injected into the ReAct node as a SystemMessage for personalised responses
{
  "liked_series": ["Mythical", "Portraits"],
  "mentioned_artworks": ["Icarus", "Voices"],
  "tone": "curious"
}
Why two layers?
SQLite holds the raw message log so the LLM can see exact conversation flow and resolve follow-up references ("tell me more about it"). The JSON preference file holds a distilled, high-level summary of what the visitor cares about — injected as system context so even the very first message of a new session feels personalised. Clearing a conversation deletes both the SQLite checkpoint rows and the JSON preference file.

LangSmith — Observability

Environment variables to set on Railway
LANGCHAIN_TRACING_V2 = true
LANGCHAIN_API_KEY    = your_key_from_smith.langchain.com
LANGCHAIN_PROJECT    = inside-the-paintbox
🔍
Full graph trace per message
Every invocation of the compiled graph appears as one trace. Drill into each node — load_preferences, classify, react_node, extract_preferences, save_preferences — and see exact inputs, outputs, and latency for each.
🔧
Tool calls are visible
Inside react_node, every iteration of the ReAct loop is tracked. See exactly which tools the LLM chose, what arguments it passed, and what the tool returned — before the LLM decided to call another tool or respond.
📊
Token counts and latency
Prompt tokens, completion tokens, and cost per LLM call. The classify node (max_tokens=5) will be very cheap; the full ReAct loop with multiple tool calls will be the most expensive step per message.
🧵
Thread-level conversation view
Traces are grouped by session. Follow a single visitor's full conversation across multiple messages, see how preferences evolved, and check whether the intent classifier was routing correctly.
⚡
Zero code changes required
LangGraph auto-detects the three LANGCHAIN_ environment variables and enables tracing. langsmith is already in requirements.txt. Set the variables on Railway, redeploy, and traces appear in real time.
